# njh-cli 교체 키트 릴리스 노트 — v1.5.477 (2026-08-27)

이번 교체 키트는 v1.5.474 이후의 반입·업그레이드 절차를 정리하고, 토큰 자동 생성·OCR tar.gz 반입·단독 게이트웨이 초기화·CPU 전용 서버의 선택적 승인 검사를 보강했습니다. njh-cli에는 파일 첨부, 중단 복구, 터미널 상태 추적과 비대화형 승인 실패 처리가 개선되었습니다.

## 이전 키트를 받으셨다면

이전 전달분은 새 키트와 섞어 사용하지 마십시오. 수신한 아카이브 파일명과 `SHA256SUMS.txt`를 먼저 대조한 뒤, 이번 `v1.5.477` 전달분의 안내와 아카이브만 사용하십시오. 체크섬 또는 파일 구성이 맞지 않으면 설치하지 말고 새 전달분을 요청하십시오.

## 토큰을 직접 넣지 않아도 설치됩니다

- Gateway와 embedding gateway 설치는 명시적으로 전달한 토큰을 먼저 사용하고, 값이 없으면 보호된 서비스 환경 파일의 기존 값을 재사용하며, 둘 다 없을 때만 새 bearer 토큰을 생성합니다. 승인된 값은 `NJH_GATEWAY_TOKEN` 또는 `NJH_EMBED_GATEWAY_TOKEN` 환경변수로 설치 전에 전달할 수 있습니다.
- 재실행해도 기존 토큰을 교체하지 않습니다. 새로 만든 값은 서비스 환경 파일에 권한 600으로 저장되며 토큰 값은 화면이나 로그에 표시하지 않습니다.
- 토큰을 문서·명령줄·로그에 직접 적지 마십시오. 값이 노출되었거나 승인 여부가 불분명하면 임의로 재사용하지 말고 새 승인값을 요청하십시오.

## 기존 설치를 보존하는 두 경로

- 이전 키트를 확인할 수 있으면 기본 업그레이드 경로를 사용하십시오. 기존 서비스를 정지하고 새 키트를 **형제 디렉터리**에 풀어 기존 키트 위에 덮어쓰지 않은 뒤, 승인된 현장값을 이관하고 완료 URL을 확인하십시오. 실패하면 기존 키트를 유지한 채 롤백할 수 있습니다.
- 기존 설치는 감지되지만 이전 키트를 더 이상 확인할 수 없는 경우에만 `NJH_BOOTSTRAP_ARCHIVE_EXISTING_INSTALL=1`을 선택적으로 사용하십시오. 먼저 `--dry-run`으로 이동 대상을 확인하십시오. 이 경로는 서비스 디렉터리를 타임스탬프가 붙은 보관 디렉터리로 이동하며 삭제하거나 덮어쓰지 않고, Ollama 모델 저장소는 이동하지 않습니다.
- 이전 키트를 확인할 수 있는데 위 환경변수를 사용하면 안전장치가 거부합니다. 보관 동작은 복구가 필요한 예외 경로로만 사용하십시오.

## OCR 반입: 서버에는 tar.gz만 전달하십시오

- 암호화된 `.7z` 파일은 반입 PC에서 엽니다. 서버로 옮길 파일은 `njh-gateway-v<버전>.tar.gz`와 `njh-ocr-engine-v<버전>.tar.gz`뿐입니다. Gateway tar.gz는 `njh-gateway-kit`에 풀고, OCR tar.gz는 그 옆에 둔 채 bootstrap을 실행하십시오.
- bootstrap이 OCR tar.gz를 자동으로 풀며, 평평한 구성과 한 단계 상위 디렉터리가 있는 구성 모두 처리합니다. OCR 엔진 파일을 Gateway 키트 안으로 임의로 복사하지 마십시오.
- OCR 콘솔은 셸 명령이 아니라 **브라우저 주소 입력창**에 `http://<게이트웨이-주소>:<포트>/ocr`를 입력해 여십시오. PC 작업은 `njh ocr <image>`와 `njh ocr doctor`를 사용하고, 인증 토큰은 승인된 환경변수로만 전달하십시오.

## 단독 게이트웨이와 llm 전용 모드

- 새 환경에서는 `node runtime/njh-gateway.js init --mode llm --home "$PWD"`로 초기화하십시오. 초기화가 TLS 인증서와 키를 자동으로 만들므로 별도의 인증서 생성 명령은 필요하지 않습니다.
- `llm` 모드는 데이터베이스 경로를 사용하지 않지만 공통 설정 구조는 유지합니다. 설정을 손으로 편집할 때 `database` 객체 자체를 삭제하지 말고, 승인된 backend와 model 값을 넣은 뒤 validate를 실행하십시오.

## CPU 전용 서버의 선택적 admission probe

- CPU 전용 서버에서 Gateway가 수행하는 admission·warm-up·복구·상주 확인 probe에만 `NJH_GATEWAY_ADMIT_THINK_FALSE=1`을 선택적으로 적용할 수 있습니다. 기본값은 꺼져 있으며 일반 채팅 요청의 추론 설정은 바뀌지 않습니다.
- 특정 ARM CPU 전용 프로파일에서 같은 10회 작업의 정확한 응답이 양쪽 모두 10/10이었고, 평균 소요 시간이 24.6초에서 3.1초로 측정되었습니다. 이는 해당 프로파일의 승인 probe 측정값이며 모든 모델·서버의 작업 품질이나 시간을 보장하는 수치는 아닙니다.

## 한 페이지 설치 카드와 배포 채널

- `docs/설치-원페이지.md`의 §2는 반입 PC에서 `.7z`를 열고 서버에는 두 tar.gz만 전달하는 순서로 다시 작성되었습니다. 서버에서 `.7z`를 여는 경로는 기본 절차가 아니라 예외적인 fallback입니다.
- 릴리스 노트는 암호화 아카이브 밖의 전달 채널에서도 먼저 확인할 수 있습니다. 아카이브를 풀기 전에 버전, 체크섬, 반입 순서를 확인하십시오.

## njh-cli 사용성 및 자동화 추적

- `/attach <local_file>`에 소스 파일을 지정하면 다음 프롬프트에 언어가 표시된 fenced context로 한 번만 포함됩니다. 이미지는 기존 업로드 경로를 사용합니다.
- 현재 응답을 멈추려면 Ctrl+C를 한 번 누르십시오. 입력 프롬프트가 복구된 뒤 다음 요청을 계속할 수 있습니다. 터미널 크기를 바꿔도 완료된 상태 줄이나 spinner 잔상이 남지 않습니다.
- 자동화 실행에서는 최종 `terminal_reason`을 확인해 정상 완료, 중단, 증거 부족을 구분하십시오. 레거시 stop 또는 exit 값만으로 성공을 판정하지 마십시오.
- 비대화형 실행에서 승인이 필요한 작업이 거부되면 남은 반복 예산을 소모하지 않고 안전하게 중단합니다. 승인이 가능한 대화형 채널이나 사전 승인된 정책에서 다시 실행하십시오.

## 알려진 제한

- OCR smoke와 모델 admission은 정해진 로컬·인증·응답 조건만 확인합니다. 실제 업무 문서 전체의 인식 정확도, 현장 권한, 일반 작업 품질을 대신 보증하지 않습니다.
- 현장 주소, 토큰, 암호, 인증서 값은 수신자 문서에 포함하지 않습니다. 승인값이 없거나 채널 검증이 실패하면 임의의 이전 값을 사용하지 말고 담당자에게 새 전달분을 요청하십시오.
